# ORスケジューラ 要件・議論ログ

## 1. 概要
本アプリは、手術室の枠管理を「診療科部長」「手術室管理者」の立場で扱えるように設計した。目的は、手術枠の空き、共有、引き受け、通知、履歴といった運用を見える化し、他診療科との競争と調整をわかりやすくすることにある。

## 2. 議論で明確になった要件

### 2-1. 入力手順と役割の明確化
- ユーザーが迷わないように、画面遷移を「自科の枠確認 → 週次グリッド → 空き枠ボード」の順で整理した。
- 立場を明示し、診療科部長と手術室管理者で表示内容と権限を分離した。
- 管理者は全診療科の状況を確認でき、部長は自科の枠に限定して扱えるようにした。

### 2-2. 権限と安全性
- 自診療科以外の枠を勝手に開放できないようにし、自科のみ解放可能とした。
- 自科部長の切り替え時には他診療科の切り替えパスワードを要求し、demoとして 1234 を採用した。
- 管理者は全診療科の枠閲覧・監視が可能である一方、各部長の所属診療科の管理範囲は保持する。

### 2-3. 学会・不在と自動共有
- 学会・不在登録を行うと、当該診療科が保有していた枠が一致する日付・曜日に応じて自動で空き枠化されるようにした。
- 空き枠は理由を付与し、ポジティブ/ネガティブ/その他で分析しやすいようにした。
- 共有された枠は、当事者と他科の意思決定を整えるために「空き枠ボード」に可視化した。

### 2-4. 競争と通知
- どの枠が、どの診療科から、どの診療科に移ったかがすぐわかるように、通知文を簡潔な一文に統一した。
- 通知は「どの枠」「どの診療科から」「どの診療科へ」「ご協力ありがとうございます。」を含む文面に整理した。
- 全科共有の通知頻度は管理者が設定できるようにした。
- 承認権限は手術室管理者に限定し、管理者が承認した場合にのみ、設定した頻度で各診療科部長へ通知が送られるようにした。
- 各診療科部長の通知一覧では、送信予定と送信済みを区別して確認できるようにした。

### 2-5. 分析可能性
- 一度通知した枠移動は二重通知しないようにした。
- すでに完了した枠移動は「済みリスト」へ移し、分析用の履歴を残すようにした。
- これにより、学会・不在・割り当て・再配置の傾向を後から見取りやすくした。

### 2-6. 管理者の観点
- 管理者は全診療科の空き枠状況を見られる必要がある。
- そのため、管理者画面では診療科フィルタと日別ビューを併用できるようにした。
- さらに、日別空き枠は帯形式で表現し、手術室番号・保有診療科・空いている時間帯が一目でわかる構成にした。
- 管理者のデフォルト表示は、日別の空き枠ビューを採用した。

### 2-7. 更新周期
- 手術枠の更新は年次更新だけでなく、3か月更新や6か月更新も想定できるように保持した。
- これは今後の運用調整や季節性変動への対応に役立つ設定として扱う。

### 2-8. 予定手術の所有権と他科侵入防止
- 予定手術の枠は当該診療科の「自分たちの枠」として扱い、他診療科からは編集・追加・削除をできないようにした。
- 既に開放された枠に対しては他科が引き受け可能だが、元の所属診療科の予定手術自体は自身の責任範囲でのみ管理する運用とする。
- これは枠の共有を促しつつ、診療科同士が他科の予定を勝手に書き換えないようにするための重要な役割制約である。
- また、閲覧は可能であっても、編集権限を持たない診療科には「追加」ボタンや編集操作を隠し、視覚的に自科の境界を明確にした。

### 2-9. 役割ごとの最小表示と承認フロー（2026-10-04 追加）
- 診療科部長: 「自科の枠」「週次グリッド」と不在登録のみ。他科が共有した空き枠は自科の枠の先頭に表示し、ワンクリックで引き受け申請できる。
- 手術室管理者: 「全体の空き状況（今週/来週/再来週）」「承認・空き枠」「週次グリッド」「分析」。承認待ちはどの画面でも上部に表示し、ワンクリックで承認/却下できる。
- 部長の「引き受け」は承認待ちの申請となり、手術室管理者の承認で確定する（管理者による割当は即時確定）。
- 過去日の枠には共有・引き受け操作を出さない。土日は翌週を「今週」として扱う。

### 2-10. 分析用データの蓄積
- 画面に出さない操作も含め、全操作をイベントログ（localStorage `or_event_log`）に追記専用で記録する。取消・却下されたデータも残る。
- 記録項目: 共有（理由・リードタイム）、申請、承認/却下（判断までの時間・競合数）、取消、管理者割当、手術の登録/更新/削除、不在登録、ログイン/切替。
- 分析タブで集計を表示し、CSV/JSON で書き出せる。

## 3. 実装済みの変更まとめ
- ロール選択画面とログイン制御を導入
- 診療科部長／手術室管理者の見える範囲を分離
- 自科のみの枠開放権限を実装
- 学会/不在登録で自動で空き枠共有
- 理由（ポジティブ/ネガティブ/その他）を記録
- 全科通知の頻度設定を追加
- 調整済み枠の履歴化と重複通知防止
- 管理者の診療科フィルタ付き日別空き枠ビューを追加
- 日別空き枠を帯表示で簡易可視化
- 更新周期の設定（年次/3か月/6か月）を追加
- 他診療科の予定手術に対する追加・編集・削除権限を制限

## 4. 残された課題
以下は今後の実運用で解決すべき課題として残す。

1. 更新周期の設定を実際の枠更新ロジックに接続する
   - 現状は設定項目として残しているが、運用ルールとして自動反映するには、更新時期や再配分ルールを明文化する必要がある。

2. 履歴データの分析機能を強化する
   - 「どの理由で枠が空いたか」「どの診療科が獲得しているか」「どの時期に多いか」をCSVやグラフで分析できるようにする余地が残る。

3. 実運用向け認証の導入
   - 現在は demo 手順としてパスワード 1234 を使っているため、本番運用に向けたID/認証基盤の導入が必要。

4. 実際の不在登録データとの連携
   - 手術室管理者が所属部署や学会情報を外部データから取り込めるようになると、運用負荷がさらに下がる。

5. 共有ルールの明文化と通知のスケジュール管理
   - 通知頻度だけでなく、誰がどのタイミングで通知を送るかの運用フローを定義する必要がある。
